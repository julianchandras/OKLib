### HDFS-16547

In this case a NameNode that is still in safe mode can be transitioned to the
observer state, so it begins serving client reads from a namespace it has not
finished loading. Fixed by `8f971b0e541`, which adds a guard to
`NameNode.transitionToObserver()`:

```java
if (notBecomeActiveInSafemode && isInSafeMode()) {
  throw new ServiceFailedException(getRole() + " still not leave safemode");
}
```

Unlike the other cases in `experiments/reproduce/`, this one runs
**pseudo-distributed on a single node**: two NameNode JVMs, no datanodes, no
ZKFC, no journalnodes. `TestDFSHAAdminMiniCluster` builds with `numDataNodes(0)`
and the bug never touches a block, so nothing is lost by collapsing the cluster.

#### Modify config

Nothing to edit for a single-node run. `core-site.xml` and `hdfs-site.xml` here
are already localhost-only; the trigger script copies them into place. Paths all
sit under `/localtmp/julian/hdfs-16547-data`, which the trigger wipes on start.

Two settings carry the experiment and should not be changed casually:

- `dfs.ha.nn.not-become-active-in-safemode=true` — the guard is a no-op without it
- `fs.defaultFS=hdfs://okcluster` — a *logical* HA URI. `DFSAdmin.setSafeMode`
  only fans out to every NameNode in the nameservice when the URI is logical,
  and it sends `isChecked=false`, which becomes `OperationCategory.UNCHECKED`
  and is therefore accepted by a **standby**. That is what makes
  `dfsadmin -safemode enter` equivalent to the unit test's
  `NameNodeAdapter.enterSafeMode(nn, false)` without any test hook.

#### Run commands (~15min build, ~90s run)

Build the buggy version (parent of the fix) into its own git worktree:

```bash
experiments/reproduce/HDFS-16547/install_HDFS-16547.sh \
    [path_to_OathKeeper] [path_to_HADOOP] [worktree_path]
```

Then reproduce:

```bash
experiments/reproduce/HDFS-16547/trigger_HDFS-16547.sh \
    [path_to_OathKeeper] [worktree_path]
```

Reproduction succeeded if the last block reads:

```
=== final state ===
localhost:8020    observer
localhost:8022    standby
```

with `transitionToObserver exit code: 0`. On the fixed build the command exits
non-zero, prints `transitionToObserver failed! NameNode still not leave
safemode`, and nn1 stays `standby`.

Confirm the observer really is still in safe mode:

```bash
HADOOP_CONF_DIR=/localtmp/julian/hdfs-16547-data/conf-nn1 bin/hdfs dfsadmin -safemode get
# Safe mode is ON in localhost/127.0.0.1:8020   <-- while state is 'observer'
```

#### Three things that bite on a single node

1. **NameNode identity.** Both NNs bind `localhost`, so `DFSUtil.getSuffixIDs`
   cannot tell them apart and aborts with *"Configuration has multiple addresses
   that match local node's address"*. `HAUtil.getNameNodeId` honours
   `dfs.ha.namenode.id` ahead of address matching, but reads it from
   `Configuration` — **a `-D` JVM flag does not work**. Each NameNode therefore
   gets its own `HADOOP_CONF_DIR` (`conf-nn1`, `conf-nn2`), built by `make_conf`.
2. **Per-host state.** `HADOOP_PID_DIR` and `HADOOP_LOG_DIR` are per host, not
   per namenode; two NNs on one box otherwise share
   `hadoop-$USER-namenode.pid` and clobber each other's bookkeeping.
3. **Namespace directories.** `dfs.namenode.name.dir` is in
   `NameNode.NAMENODE_SPECIFIC_KEYS`, so `dfs.namenode.name.dir.okcluster.nn1`
   and `.nn2` resolve per namenode even though both JVMs read one
   `hdfs-site.xml`. `dfs.namenode.shared.edits.dir` is left unsuffixed on
   purpose — that one is meant to be shared.

#### Build note

The 3.4.0-SNAPSHOT reactor contains three `hadoop-yarn-applications-catalog`
modules; the webapp runs `yarn install` against the npm registry and fails
offline, and catalog-docker depends on its war, so all three are excluded.
Nothing under `hadoop-dist` depends on them. The `hadoop-yarn-project`
aggregator still wants that war and fails at module 67, while *Apache Hadoop
Distribution* is module 105 — so the build **needs `-fae`**, otherwise the
reactor stops and no dist is produced. Expect 109 SUCCESS of 110 with one
FAILURE on `hadoop-yarn-project`. Because yarn is skipped, `share/hadoop/yarn` is absent and
`hadoop_bootstrap` aborts with *"Invalid HADOOP_YARN_HOME"*; it is only a `-d`
test, so the trigger creates the empty directory.
